OTA updates ​

Some apps can update themselves: React Native, Flutter, and Electron-style apps ship a runtime that applies new content and logic without waiting on a store review. For those, ShipperDog distributes OTA (over-the-air) updates — platform-agnostic bundles governed, signed, staged, and monitored with exactly the same rigor as store releases.

The choice is mechanical: send what the app can apply at runtime (a JS bundle, refreshed assets) as an OTA bundle; send anything that changes the native binary through the ordinary store-release path. An OTA bundle is never a side channel — it rides the same releases, approvals, and gates everything else rides.

OTA is opt-in per application: the application's OTA toggle is turned on in the console, and the app gets an app-scoped Ed25519 signing key (the private half stays inside ShipperDog's secret store; the public half is copyable from the console for embedding in the app).

From bundle to release ​

An OTA update is a bundle with its own lifecycle:

StageWhat is true
DraftThe author uploads a platform-agnostic archive; it gets its own version row, a version label, a platform tag, and a minimum store version.
SignedFinalize computes the sha256 and size, then signs with the app's Ed25519 key. Only a signed bundle can publish.
ReleasedThe bundle publishes on an ordinary release over a ring whose distribution channel is ota — exactly one bundle per OTA release.

Because an OTA release is an ordinary release, the whole governance stack applies unchanged: approval workflows, quality gates, policies, and status history all guard it, and the release dashboard reads the same as any other. Widening the audience is the same ring promotion; pulling it back is the same rollback crossing.

Two withdrawal rules follow from that linkage: a signed-but-unreleased bundle is the author's to revoke, while a released bundle belongs to its release — pulling it back is the release's rollback, not a bundle delete. The rollout can also be halted (below), which stops new devices from seeing the update without touching the release.

The device flow ​

The shipped app carries an sdc1. app token — an identifier, not a secret — and polls one endpoint, GET /api/v1/ota/check, on a server-owned cadence (the manifest returns pollIntervalSeconds, default 3600):

The manifest tells the device everything it needs:

MemberMeaning
bundleId / bundleVersionThe served bundle's id and version label — every lifecycle report attributes back through bundleId.
urlA short-lived signed download URL, minted for this check.
sha256 / sizeBytesVerify the downloaded bytes end to end.
signature / keyIdThe Ed25519 signature over the sha256, and which signing-key generation made it.
forced / minAppVersionWhether the update must apply, and the oldest store version it applies to — defaults from the bundle, overridable per release target.
ingestTokenA short-lived sdt1. grant for reporting this update's lifecycle.
pollIntervalSecondsWhen to check again.

The 204 is deliberately opaque: up to date, not eligible, a paused or halted rollout, a stage the device has not reached, or no live release — all the same bytes, because the split lives in ShipperDog's server-side counters, never on the wire. A malformed request is the one coded error the check returns; a bad token is the ordinary 401.

Verification is end to end: the device checks the sha256 and the Ed25519 signature against the public key embedded in the app — the signature is never just transport trust. Signing keys rotate by generation: a new keyId supersedes, and old signatures stay verifiable against the retained public half until the generation retires.

Staged device rollout ​

One rollout plan per OTA release: a ladder of cumulative stages, each a basis-point threshold (10000 = everyone), advanced manually or automatically per the plan's mode. Which devices a stage covers is decided on the fly, deterministically:

hash(deviceId, planSalt) mod 10000 < stage.basisPoints

The same device lands in the same bucket for the life of the plan — no cohort table, nothing to backfill — and a device below the current stage's threshold gets the same 204 as an up-to-date device.

StandingWhat it means
RunningStages admit devices per the ladder.
PausedDevices hold; already-served devices keep their manifest.
HaltedThe human stop. Every control crossing is audit-trailed.
CompleteThe ladder reached everyone.

Pause, resume, advance, and halt are one-action controls from the console or CLI. Halting is deliberately manual: alert rules watch failure rates and crash-free regressions and page a human through the notification bus, but no threshold ever stops a rollout by itself — the halt is one audited action away.

Watching the funnel ​

The funnel's two halves come from different places by design. Checks are counted server-side; the device-side journey — seen, download, apply, fail, roll back — is reported by the app as lifecycle telemetry through the ordinary analytics ingest. The OTA dashboard reads both halves together, and alert rules turn degradation signals into notifications for a human to act on.

v1 ships full bundles only: a device always downloads the complete archive. Delta bundles are a recorded future direction, not current behavior.
