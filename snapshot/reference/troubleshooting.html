Troubleshooting ​

The ten scenarios support actually sees, each as symptom, likely cause, and fix. Codes you meet along the way are explained in error codes; the vocabulary lives in the glossary.

The CLI exited non-zero ​

The exit code is a stable contract pipelines branch on — read it first, then the printed problem.

ExitWhat it saysFix
1Server-side/5xx failureRetry; if it repeats, report the trace id.
2Usage — bad flags, missing args, unresolvable nameCheck the command shape against the CLI reference.
3Auth — no credentials, or 401Mint a fresh PAT; shipperdog login or set SHIPPERDOG_TOKEN.
4Validation — the API refused the request (4xx), or validation settled FAILEDRead the problem's code in error codes.
5Network — refused, DNS, timeoutCheck the API URL (--api / SHIPPERDOG_API) and connectivity.

The portal signed me out and 401s everything ​

SymptomLikely causeFix
Working session turns to UNAUTHENTICATED/INVALID_TOKEN on every actionThe access token expired or was revoked mid-sessionSign in again; the portal keeps your place. If it repeats immediately, ask your admin whether your account was suspended or the session's refresh family was revoked (for example by an IdP-initiated logout).

A 404 for something you know exists ​

SymptomLikely causeFix
An app, version, release, or feedback row 404s for you but not a colleagueConcealment, not absence: without membership/grant/role you receive the byte-identical 404 a genuine miss producesVerify your tenant membership and grant; the resource's owner or an admin can compare in the audit trail
A release detail 404s right after creation in CIWrong application scope in the CLI reference (--app)Re-run with the application that owns the release

The invitation page says the link is invalid ​

SymptomLikely causeFix
"Open the link from your email" on the join pageLink expired (seven days) or already used — links are single-useAsk your team for a fresh invitation (accept an invitation)
Fresh link still refusesThe email you typed on the join card differs from the invited addressUse exactly the address the invitation was sent to

SSO login does not complete ​

The redirect leaves the IdP and lands nowhere useful — one of the handshake facts disagrees between the IdP and the organization's IdP configuration (configure SSO).

SymptomLikely causeFix
IdP shows an error before redirectingClient ID or redirect URI mismatch on the IdP applicationCopy the console's SP metadata into the IdP app exactly
Redirect lands on an error pageIssuer URL typo, or enabled is still falseRe-check issuerUrl against the IdP's real issuer; enable the record when tested
One user's login lands in the Console, another's bounces back to sign-in with an SSO errorProvisioning posture: INVITED_ONLY admits members only — and every SSO refusal, whatever its cause, answers the same uniform bounce (the distinct reason rides the audit line)Add the member first, or switch to JIT deliberately (its default role is the VIEWER floor)
Group role mappings never applygroupClaimName does not match the token's claimName the claim exactly as the IdP issues it

SCIM answers 401 to everything ​

The SCIM surface's 401 is uniform by design — no response ever hints which leg refused, so the fix is a checklist, not a probe (configure SCIM).

SymptomLikely causeFix
Every push from the IdP gets 401The connector token in the IdP differs from the one in ShipperDog's SCIM configRe-copy the token, or rotate it in the console and update the IdP
Worked yesterday, 401 todayThe token was rotated on one side onlyRe-sync both sides
Need to know which leg refusedThe distinct reason rides the audit line, never the responseAn administrator reads the SCIM audit entries

Webhook deliveries all fail 401 — or one hits 413 ​

SymptomLikely causeFix
Every delivery from GitHub/Jenkins/GitLab answers 401 WEBHOOK_SIGNATURE_REJECTEDThe shared secret differs between sender and receiver, or no secret is configured at the receiverSet the identical secret on both sides (inbound webhooks)
Sporadic 401s from the same senderStale-timestamp replay defense: the sender's clock drifts outside the windowFix the sender's clock skew
Store deliveries (App Store/Play) answer 400 WEBHOOK_DELIVERY_REJECTEDProvider token/audience verification failedRe-check the provider's signed-configuration on the receiver
A delivery answers 413 WEBHOOK_PAYLOAD_TOO_LARGEBody over the payload ceiling (default 25 MB)The provider must stay under the ceiling — GitHub's own cap matches

A gate is stuck "no data yet (fail-closed)" ​

SymptomLikely causeFix
Required gate blocks with no result ever recordedNo result submitted — the gate needs a pass/fail with a mandatory evidence URL from your pipelineSubmit it from CI: shipperdog gate result R-… <type> --status pass --evidence-url …
Metric-backed gate (crash-free-threshold, open-critical-bugs) has no valueIt resolves from analytics, not submissions — missing feeds leave it fail-closedLet the analytics feed land, or override once with an audited reason
open-critical-bugs stays redFeedback reports sit untriaged — the gate reads the live feedback blockTriage the reports; the next evaluation re-reads

The download link expired mid-install ​

SymptomLikely causeFix
"Link expired" moments after tapping DownloadSigned URLs live minutes by design; the pause took too longTap Download again — a fresh URL is minted per request
Fresh links also refuse, "build not available"The release was rolled back or the grant revoked while you were installingThat is distribution being cut, not a bug — the team decides what re-opens access (rollback)

Promotion answers 409 with a blocker list ​

SymptomLikely causeFix
RELEASE_PROMOTION_BLOCKED with gates/approvals/eligibility namedThe target ring's evaluation refused the hop — every blocker is listed with evidenceRun shipperdog release precheck <id>; fix each named blocker, promote again (promote through rings)
RELEASE_PROMOTION_RING_SKIPThe hop tried to jump a ring — one ring at a time is the defaultPromote to the next ring; skips only if your organization explicitly allowed them
RELEASE_PROMOTION_RING_SPLITThe selected targets sit on different rings (a prior selective promotion split them)Promote ring group by ring group
RELEASE_PROMOTION_CONFLICTA concurrent promotion moved the targets firstRe-read the release and retry — nothing partial committed

When reporting anything

Quote the trace id from the toast or the CLI output. It joins your failure to the exact server-side events — the difference between a ticket and an answer.
